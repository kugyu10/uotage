# ADR: [移行 P5] D1 移行後のトランザクション設計（issue #11）

- 状態: 提案（実装前。P4 の実運用計測を経てから着手する）
- 決定: **方式A（Durable Objects によるテナント単位の直列化）を主軸に、外部作用（メール送信・Stripe）には方式Bの冪等キーを併用する**

## 背景

D1 は auto-commit で、原子性が保証されるのは `batch()` に一括で渡した文の列だけ。
`register_reader`（約95行）/ `process_stripe_purchase`（約65行）/ `import_scenario_readers`（約186行）は
いずれも「読む → JS で判断 → 複数テーブルに書く」型の PL/pgSQL で、途中に JS の分岐を挟めない
`batch()` にはそのまま乗らない。

## 検討した方式

### 方式A: Durable Objects（DO）で書き込みを直列化 — 採用

テナント単位の DO を置き、上記3関数に相当する書き込みはすべて DO 経由にする。
DO はシングルスレッドなので「読む → 判断 → batch() で書く」の間に他の書き込みが割り込まない。
`FOR UPDATE` が担っていた行ロックの代替になる。

- 採用理由
  - 3関数の**制御フローをほぼそのまま移植できる**（判断ロジックの組み替えが不要）。
    方式B単独だと3関数それぞれを補償可能な段階に分解し直す必要があり、移植の正しさを
    Postgres 版と突き合わせる作業（issue の完了条件）が難しくなる
  - 「読者登録が同一読者で同時に走る」「インポートと登録が同じ読者を触る」といった
    競合を、コードではなく実行モデルで排除できる
  - 書き込みの最後の `batch()` は D1 側で原子的なので、DO が途中でクラッシュしても
    中途半端な書き込みは残らない（読み→判断の途中で落ちた場合は単に何も書かれない）
- トレードオフ（受け入れる）
  - テナント単位の直列化はスループット上限になる。ただし現状は少人数テナントの MVP で、
    書き込みの絶対量（登録・購入・インポート）は毎分数件のオーダー。問題になるのは
    Phase 7 のマルチテナント拡大後で、そのときは DO を reader 単位に細分化する逃げ道がある
  - Cloudflare 固有機能への依存が深まる（切り戻しコスト増）。P4 の計測で D1 自体を
    見送る判断になれば本 ADR ごと破棄する

### 方式B: 冪等キー＋補償処理 — 単独では不採用、外部作用にのみ併用

- 不採用の理由: 3関数すべてを「途中で落ちても壊れない」段階列に再設計する必要があり、
  移植の検証（Postgres 版と同じ結果を返すこと）が事実上「新規実装の検証」になる。
  事故防止が最重要とされる CSV インポート（要件定義書 10.2）でこのリスクを取りたくない
- 併用する部分: DO で直列化しても**外部作用は巻き戻せない**。ここは現行設計の冪等性を維持する
  - メール送信: Resend の Idempotency-Key（現行 dispatch と同じ）
  - Stripe: `stripe_session_id` の UNIQUE（現行 `process_stripe_purchase` と同じ）
  - キュー投入: `UNIQUE(scenario_reader_id, step_message_id)`（P4 の D1 スキーマで維持済み）

## RLS の代替（このリポジトリに実装済みの部分）

`src/lib/d1/tenant-db.ts` の `createTenantDb(executor, tenantId)` を D1 アクセスの唯一の入口にする。

- テナント分離対象テーブルに触れる SQL は `tenant_id = :tenant` マーカーが無いと実行前に例外
- `:tenant` には呼び出し側が渡した tenantId がそのまま入る。**これは呼び出し規約であり、
  型レベルでは強制していない**。`createTenantDb` は空でない文字列であれば何でも受け取る。
  「認証済みオペレーターの tenantId（`requireOperator` 相当で解決した値）だけを渡す」ことは
  呼び出し側の責務として doc コメントで明記するに留まる（PR #22 レビュー 🟢11 対応:
  当初の記述はここを型で保証しているかのように読めたため修正した）
- 越境テスト（`test/unit/d1-tenant-db.test.ts`）を CI で回す
- 限界も明記している: join の各テーブルまでは静的検査しない／意図的な迂回は防げない。
  これは「付け忘れ事故」を防ぐ装置であり、`is_tenant_operator()` が担っていた
  「認証ユーザー→テナント」の解決はアプリ層のガード（現行 `requireOperator`）が引き続き担う

## DO を経由しない書き込み経路（PR #22 レビュー 🟡6 対応）

方式Aは「上記3関数に相当する書き込みはすべて DO 経由にする」としているが、
このシステムには DO を通らない書き込み経路が既にある。DO 内の「読む → 判断 → `batch()` で書く」の
読み取りと、これらの経路の書き込みは実行モデルレベルでは競合しうるため、経路ごとに扱いを決める。

- **毎分 cron の配信ディスパッチ**（`supabase/cron/dispatch-deliveries.sql` の `claim_deliveries`。
  P4 で D1 側へ移植予定）: `deliveries` を直接 claim・更新する。3関数側（特に `register_reader` の
  キュー投入）と `deliveries` を共有するため、(a) DO 経由に寄せるか、(b) `claim_deliveries` 側を
  `status` 列の CAS（`update ... where status = 'pending'` のような楽観ロック、現行実装が既にこの形）
  に保つかを、P5 着手時に選ぶ。現行の `claim_deliveries` は行単位の CAS で更新しており、
  DO 側が `deliveries` に書く操作（新規 INSERT が中心）と行が重ならない限り実害は無いと見込むが、
  **P5 着手時に「DO 側が deliveries の既存行を UPDATE するケースが無いこと」を確認すること**。
- **Stripe webhook**（`process_stripe_purchase` 系）: 外部から任意タイミングで叩かれる。
  webhook ハンドラ自体を DO 経由に寄せる（方式A の対象3関数の1つなので、実装時に自然と DO 経由になる）。
- 上記いずれも、移植時点で「DO 側と書き込みが重なる行が無い」ことをテストで固定できない場合は、
  `deliveries` の該当列に楽観ロック（バージョン列 or CAS 条件）を追加する方針とする。

## この決定が覆る条件

- P4 の実測で D1 のレイテンシ・rows read 課金が想定を超えた場合（D1 自体を再検討）
- DO の料金・レイテンシが毎分 cron と噛み合わない場合（方式Bの全面採用を再検討）
