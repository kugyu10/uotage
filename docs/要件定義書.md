# **要件定義書：ステップ配信／デッドラインファネル特化型 自作マーケティングツール**

> **バージョン:** 3.0
> **更新日:** 2026-08-12
> **v2.0からの主な変更:** **UTAGEのユビキタス言語に全面的に準拠**（リード→読者、シーケンス→シナリオ、ステップメール→ステップ配信 等）。**ラベル機能**を追加。**UTAGEとの双方向CSV連携**（10章）を追加。管理画面のナビゲーション構造をUTAGEに合わせて再定義。テナント関連の命名を `tenants` / `operators` / `delivery_accounts` に分離。
> **v1.0からの主な変更:** ステップ配信機能の追加、個別相談への導線の追加、購入起点デッドラインの追加、マルチテナント前提のスキーマ化、動画ホスティングの方針変更、Cron基盤の変更、管理画面の追加、配信停止・送信ログの追加、契約プランの制限値の明記。

## **1. プロジェクト概要**

### **1.1 目的**

高額なSaaS（UTAGE等）に依存せず、ランニングコストを極小化しつつ、以下2つのファネルを自動化するシステムを構築する。

1. **プレゼント（リードマグネット）ファネル**
   無料プレゼントの受け取りをきっかけにステップ配信を行い、**個別相談**へ誘導する。
2. **購入者ファネル**
   フロント商品（動画）の購入をきっかけにステップ配信を行い、**購入から一定期間限定の個別相談オファー**（カウントダウンタイマー付き）を提示する。期限が過ぎたら申し込みできなくなる。

加えて、**自分用とクライアント用でデータを分けられる**構造を最初から持たせる。

### **1.2 背景**

メインの配信基盤は Substack だが、Substack には標準のステップ配信機能がない。本ツールはその代替として、ステップ配信とデッドラインファネルを担う。

### **1.3 UTAGEとの関係（重要な前提）**

本ツールは「ミニ版UTAGE」として、**将来UTAGEへ移行する、あるいはUTAGEから移ってくることを見据えて設計する**。そのため以下を方針とする。

* **ユビキタス言語はUTAGEの正式用語に寄せる**（1.5 の対応表を唯一の正とする）
* **管理画面のナビゲーション構造もUTAGEに寄せる**（4.2）
* **UTAGEとの双方向CSV連携を機能要件に含める**（10章）

> 目的は、①UTAGEに触れたときに自分もクライアントも用語で迷わないこと、②乗り換えの際にデータとシナリオ設計をそのまま持ち運べること、の2点。

### **1.4 スコープ（対象範囲）**

* **対象:**
  * 読者の取得（オプトイン）
  * **ステップ配信（複数通シナリオ）**
  * **ステップ配信のGUI編集（管理画面）**
  * **ラベル**（付与・閲覧・エクスポート）
  * 期限付きオファー提示（カウントダウンタイマー）
  * **個別相談への導線（外部予約ツールへの誘導）**
  * Stripe決済
  * 購入者向けコンテンツ提供（会員サイト相当）
  * メルマガ解除（配信停止）
  * テナント単位のデータ分離
  * **UTAGEとの双方向CSVインポート／エクスポート**

* **対象外（やらないこと）:**
  * LPビルダー機能（※MVPではページはアプリ内の静的ページとしてコードで作成する）
  * LINE配信 / SMS配信（**UTAGEの「配信アカウント」がメール・LINE併用を前提とするため、将来の拡張余地だけ残す**）
  * イベント・予約機能（自作の予約カレンダー）
  * パートナー機能（アフィリエイト）
  * 自動ウェビナー
  * 複雑な会員サイト（コース進捗管理、バンドルコース）
  * Substack との API 連携・購読者同期
  * 開封率・クリック率の計測
  * バウンス／苦情（complaint）の自動処理
  * 期限切れ後の「再オファー希望」受け皿フォーム
  * **ラベルによる配信条件分岐**（ラベルの付与と閲覧のみ行い、「このラベルの読者だけに配信」は後回し）
  * **アクション設定のフル機能**（UTAGEのシナリオ遷移・複合アクション。※4.3-4 の送信条件フィルタのみ実装する）

### **1.5 ユビキタス言語（UTAGE準拠）★本ドキュメントの基準**

#### **UTAGEに対応語が存在しない概念**

| 概念 | 本ツールでの呼称 | 理由 |
| :---- | :---- | :---- |
| 自分用／クライアント用の**データ分離単位** | **テナント**（`tenants`） | **UTAGEにテナント分離の概念は存在しない。** UTAGEでクライアントごとに分ける場合は**UTAGEの契約自体を別に取る**のが標準。「アカウント」という語はUTAGE内で「契約アカウント」「配信アカウント」「オペレーターアカウント」の3義に酷使されているため、テナントに流用すると確実に混乱する |

> **移行時の対応:** **1テナント ＝ 1 UTAGE契約**。テナントをまたぐデータ移行は発生しない（10.3 参照）。

#### **紛らわしい語の注意**

* **「配信アカウント」はテナントではない。** UTAGEの配信アカウントは「メールのみ／LINEのみ／メール・LINE併用」を選ぶ**送信チャネルの単位**であり、シナリオの親にあたる。本ツールではメールのみのため実質1件だが、将来のLINE対応と送信元ドメインの持ち場所として `delivery_accounts` を用意する
* **「オペレーター」は権限を絞ったサブユーザーであり、テナントの分離ではない。** UTAGEのオペレーターは同一契約のデータを共有する（機能単位で表示/非表示を制御するだけ）。代理運用の分離には使えない
* **「パートナー」はアフィリエイター**であり、クライアントのことではない

### **1.6 MVPとフェーズ2の線引き（決定事項サマリ）**

| 論点 | 決定 |
| :---- | :---- |
| テナント分離 | **MVPは自分専用**。ただしDBスキーマには最初から `tenant_id` を持たせ、後から画面を足せる状態にする |
| 読者の取得経路 | **自作の登録フォームのみ**。Substack とは連携しない |
| ページの作成方法 | **MVPはこのアプリ内の静的ページ**（Next.jsでコード作成） |
| 個別相談の受付 | **外部予約ツール（TimeRex / Calendly 等）へリンクするだけ**。本ツールは「申込ページを期限で開閉する」ことのみ担当 |
| 決済 | **このツールでStripe決済**（Stripe Checkout + Webhook） |
| ステップ配信の編集 | **管理画面でGUI編集** |
| デッドラインの起点 | **2系統**（シナリオ登録起点／購入起点）をそれぞれ独立したファネルとして持つ |
| 重複登録時の期限 | **リセットしない**（初回の期限を維持し、既存トークンを再送） |
| 動画配信 | **Vimeo / Bunny 等の外部サービス** |
| 配信周辺機能 | **メルマガ解除** と **送信ログ・重複送信防止** をMVPに含む |
| **ラベル** | **付与・閲覧・エクスポートのみMVPに含む。**配信条件分岐は後回し |
| Cron基盤 | **Supabaseのスケジューラー**（pg_cron + Edge Functions）。Vercelは Hobby プランのまま |
| 管理画面ログイン | **Supabase Auth（メールリンク／マジックリンク）** |
| **UTAGE連携** | **双方向CSV**（UTAGE形式でのエクスポート、UTAGEエクスポートCSVのインポート） |

## **2. システムアーキテクチャ**

サーバーレス構成とし、保守・運用コストを最小化する。

| 領域 | 採用技術 | 契約プラン | 備考 |
| :---- | :---- | :---- | :---- |
| フロントエンド & バックエンド | Next.js (App Router) + Vercel | **Hobby** | **Cronには依存しない設計にする**（7.3 参照） |
| データベース | Supabase (PostgreSQL) | **Pro（契約済み）** | RLSでテナント単位に分離 |
| 管理画面の認証 | Supabase Auth（Magic Link） | 同上 | 新規サインアップは無効化。招待/手動作成のみ |
| メール配信 | Resend | **Pro（契約済み）** | 独自ドメイン認証（SPF/DKIM/DMARC）必須 |
| **バッチ処理（送信キュー）** | **Supabase pg_cron + Supabase Edge Functions** | 同上 | **1分間隔**で送信キューを処理。Vercel Hobbyの「Cron 1日1回・±59分」制限を回避するため |
| 動画ホスティング | **Vimeo / Bunny Stream 等の外部サービス** | 別途 | 限定公開＋ドメイン制限。ページ側のアクセス制御は本ツールが担当 |
| 決済 | Stripe (Checkout + Webhook) | 従量 | |
| 個別相談の日程調整 | **外部予約ツール（TimeRex / Calendly / Spir 等）** | 別途 | URLへ誘導するのみ |

> 各プランの具体的な制限値と、それが設計に与える制約は **7章「契約プランの制限値とキャパシティ」** に集約する。

### **2.1 バッチ処理の構成理由**

ステップ配信は「N日後のこの時刻に送る」処理のため、**短い間隔で送信キューを見るCron**が必須。Vercel Hobbyプランは Cron が**1日1回・実行精度±59分**に制限されており（7.3）、ステップ配信の用途には使えない。したがって送信キューの処理は Supabase 側で完結させる。

Supabase Pro の Edge Function 実行枠は月200万回で、**1分間隔で回しても月43,200回（枠の約2.2%）**にしかならないため、精度を最優先して**1分間隔**を採用する。

```
pg_cron（1分ごと）
  └─→ Supabase Edge Function: dispatch-deliveries
        ├─ deliveries から「scheduled_at <= now() & status=queued」を最大500件抽出
        ├─ 抽出した行を status=processing に更新（他プロセスとの競合を防ぐ）
        ├─ 送信条件フィルタ（メルマガ解除/購入済み/シナリオ停止）→ 該当は status=skipped
        ├─ 本文の置き換え文字を解決（テンプレートレンダリング）
        ├─ Resend の Batch API で 100件ずつ送信（★ 2.2 参照）
        └─ deliveries を status=sent に更新（＋ resend_message_id 記録）
```

メール本文のレンダリング（置き換え文字の解決）も Edge Function 側で行う。これにより Next.js 側は「Webサイト＋管理画面」に専念し、送信基盤とは疎結合になる。

### **2.2 【重要】Resend は1件ずつ送らず Batch API を使う**

**Resend の API レート制限は全アカウント共通で 2 リクエスト／秒**（プランによらない）。1通ずつ `POST /emails` を叩く実装にすると **毎秒2通しか送れず**、500通の配信に250秒かかって Edge Function の実行時間上限（400秒）に迫る。

そのため、送信は必ず **Batch API（`POST /emails/batch`、1リクエストにつき最大100通）** を使う。

* 500通 = **5リクエスト**。レート制限2req/secでも約2.5秒で完了する
* Batch API は **添付ファイル（attachments）に非対応**。→ プレゼントは**添付ではなくダウンロードURLで配布する**設計とする
* Batch API は **Idempotency Key に対応**（有効期限24時間）。DB側の `UNIQUE(scenario_reader_id, step_message_id)` を主とし、Resend 側の Idempotency Key を副として二重に重複送信を防ぐ
* Resend の `scheduled_at`（予約送信）は**使わない**。Resend側に予約を積むと、メルマガ解除や購入によるスキップが発生した際に個別のキャンセルAPIを叩く必要が生じるため、送信タイミングの制御はDB（`deliveries`）に一元化する

## **3. ユーザーフロー**

### **3.1 フロー A：プレゼント（リードマグネット）ファネル**

1. **登録フォームから登録**
   見込み客がアプリ内のページの**登録フォーム**にメールアドレスを入力して送信。

2. **読者登録 & シナリオ登録**
   * `readers` レコードを作成（既存なら再利用し、**期限はリセットしない**）
   * `access_token`（URL用ランダム文字列）と `unsubscribe_token` を発行
   * 該当ファネルのシナリオに `scenario_readers` として登録し、`deadline_at`（登録時刻 + N時間）を確定
   * **登録経路**（`registration_path`）を記録
   * **ラベルを付与**（例：`プレゼントA登録`）
   * シナリオの全ステップ分の `deliveries` を「送信予定時刻つき」でキューに積む

3. **シナリオ登録直後のステップ配信（1通目）**
   プレゼントのダウンロード／視聴URL（`?token=xxx`）を含むメールを送信。

4. **ステップ配信（2通目以降）**
   Supabase の Cron が送信予定時刻を過ぎたものを順次配信。各メールから **個別相談の申込ページ** へ誘導する。

5. **個別相談の申込ページへアクセス**
   Next.js のサーバーサイドでトークンと `deadline_at` を検証。
   * **期限内:** カウントダウンタイマー付きで、外部予約ツールへのボタンを表示
   * **期限切れ:** 終了ページへリダイレクト（外部予約URLは表示しない）

### **3.2 フロー B：購入者ファネル**

1. **販売ページ → 決済**
   フロント動画の**販売ページ**から Stripe Checkout へ遷移し、支払い。

2. **決済完了 Webhook**
   `checkout.session.completed` を Next.js の API ルートで受信（**署名検証必須**）。
   * `purchases` レコードを作成
   * 読者が未登録なら新規作成
   * **ラベルを付与**（例：`フロント動画購入`）
   * 会員サイト（コース）のURLをメール送信

3. **購入後に登録するシナリオを開始**
   購入をトリガーに `scenario_readers` を作成し、`deadline_at = 購入時刻 + 7日` を確定。ステップ配信をキューに積む。

4. **期間限定の個別相談オファー**
   ステップ配信から個別相談の申込ページへ誘導。**購入から7日**を過ぎると申込不可（終了ページへリダイレクト）。

5. **会員サイトで視聴**
   トークンで権限チェック後、外部動画サービスの限定公開プレーヤーを埋め込んだページを表示。

### **3.3 フロー C：メルマガ解除**

全メールのフッターにある**解除用リンク**（`?u=unsubscribe_token`）をクリックすると、`readers.unsubscribed_at` を記録し、以降その読者への全ステップ配信を停止する。

## **4. 機能要件**

### **4.1 公開側（読者が触れる画面）**

1. **登録ページ**
   * MVPはNext.js内の静的ページとしてコードで作成する（`/lp/[slug]`）
   * 特定電子メール法に基づく表記（送信者名・連絡先・プライバシーポリシーへのリンク）を含む

2. **登録フォームAPI**
   * メールアドレスの形式バリデーション
   * **重複登録時:** 既存レコードを再利用し、**期限（`deadline_at`）はリセットしない**。既存トークンを含むメールを再送する
   * 同一シナリオに既に登録済みの場合、二重にキューを積まない
   * **登録経路**を記録し、経路に応じたラベルを付与する
   * 簡易なbot対策（ハニーポット項目 + レート制限）

3. **販売ページ（デッドライン制御）**
   * サーバーサイド（SSR）での期限判定
   * クライアントサイドのカウントダウンタイマー表示
   * **タイマーの残時間はサーバーから渡した `deadline_at` を基準に算出する**（クライアント時刻に依存させない）
   * 期限切れの場合は終了ページへリダイレクト
   * 決済フォームは Stripe Checkout へ遷移させる

4. **個別相談 申込ページ**
   * 販売ページと同じ期限制御ロジック
   * 期限内のみ、外部予約ツールのURLを表示する
   * 期限切れの場合、**外部予約URLをHTMLに一切出力しない**（サーバー側で分岐）

5. **終了ページ**
   * 期限切れ読者向けの静的ページ

6. **会員サイト（コース視聴ページ）**
   * トークンによるアクセス制御 + 購入レコードの存在チェック
   * 外部動画サービスの埋め込みプレーヤーを表示
   * 動画サービス側でドメイン制限（Referer制限）を設定する

7. **メルマガ解除ページ**
   * ワンクリックで解除を確定する（確認画面は挟むが、追加のログインは不要）

### **4.2 管理画面（要ログイン）★UTAGEのナビゲーション構造に準拠**

Supabase Auth（Magic Link）で保護する。新規サインアップは無効化し、アカウントは手動作成する。

**グローバルナビゲーション**（UTAGEの上部メニューに合わせる）

```
[ファネル] [メール配信] [会員サイト] [ラベル] [管理メニュー]
```

* 決済連携設定（Stripe キー）

### **4.3 バックエンド処理**

1. **登録フォームAPI**（Next.js Route Handler）
   * 読者登録、トークン発行、シナリオ登録、ラベル付与、キュー投入、1通目の即時送信

2. **Stripe Webhook エンドポイント**（Next.js Route Handler）
   * `checkout.session.completed` を受信
   * **署名シークレットによる検証を必ず行う**
   * `purchases` 作成、ラベル付与、購入後シナリオの開始
   * **冪等性の担保:** `stripe_session_id` を UNIQUE 制約とし、Stripe のリトライで二重処理されないようにする

3. **送信キュー処理バッチ**（Supabase Edge Function、pg_cron から**1分間隔**で起動）
   * 送信予定時刻を過ぎた `deliveries`（`status=queued`）を **1回あたり最大500件** 抽出
   * 抽出と同時に `status=processing` へ更新する（`UPDATE ... RETURNING` を使い、前回実行が長引いた場合の二重取得を防ぐ）
   * **Resend の Batch API で100件ずつ送信**（2.2 参照。1通ずつ送ってはならない）
   * 結果を `deliveries` に記録（`sent_at`、`resend_message_id`、失敗時は `error_message`）
   * **重複送信防止:** `deliveries` の `UNIQUE(scenario_reader_id, step_message_id)` と、`status=processing` への事前更新の二段構えで防ぐ。加えて Resend の Idempotency Key を付与する
   * 失敗時は最大3回までリトライし、それを超えたら `status=failed` で確定させる
   * `status=processing` のまま10分以上経過した行は、異常終了とみなして `queued` に戻す（スタック行の自動復旧）

4. **送信条件フィルタ（共通）**
   以下のいずれかに該当する読者には、キューに積まれていても送信しない（`status=skipped` として記録）。
   * `readers.unsubscribed_at` が設定されている（メルマガ解除済み）
   * `scenario_readers.status` が `stopped` / `completed`
   * **ステップに「購入済みには送らない」フラグが立っており、かつ該当読者が対象商品を購入済み**
     ※ 購入済みの人に「あと3日で購入締切」が届く事故を防ぐための最小限のフィルタ。UTAGEの「シナリオ遷移（停止）」に相当する処理はMVPでは行わない

## **5. データベース設計（Supabase Schema）**

### **5.1 設計方針**

* 全てのユーザーデータテーブルに `tenant_id` を持たせ、RLS でテナント単位に分離する
* MVPではテナントは1件のみ運用するが、スキーマ上は複数前提とする
* **テーブル名・カラム名は 1.5 の対応表に従う。** UTAGEの日本語UI表記とDB名の対応が1対1になるようにする
* **期限（`deadline_at`）は `readers` ではなく `scenario_readers` が持つ。** 登録起点と購入起点の2系統の期限を同一読者が同時に持ちうるため
* **ラベルは `readers` に紐づける**（シナリオではない）。UTAGEの「ラベルは全シナリオ共通情報」という仕様に合わせる

### **5.4 RLS（Row Level Security）**

* 全テーブルで RLS を有効化する
* 管理画面からのアクセス：`operators` に自分の `user_id` が存在する `tenant_id` の行のみ参照・更新可能
* 公開ページ（販売ページ等）からのアクセス：**anon キーでは直接参照させない**。Next.js のサーバーサイドから service role キーで参照し、トークン検証を必ず経由する
* Edge Function の送信バッチ：service role キーを使用

## **6. 非機能要件**

### **6.1 セキュリティ**

* **トークン:** `access_token` / `unsubscribe_token` は暗号論的に安全な乱数（32バイト以上）で生成する。連番や推測可能な値にしない
* **Stripe Webhook:** 署名シークレットによる検証を必ず行う。検証失敗時は 400 を返して処理しない
* **service role キー:** サーバーサイド（Next.js Route Handler / Edge Function）のみで使用し、クライアントに一切露出させない
* **コース（動画）:** 外部動画サービス側で限定公開＋ドメイン制限（Referer制限）を設定し、URLが流出しても他サイトで再生できないようにする
* **管理画面:** Middleware でセッション未保持のアクセスをログインページへリダイレクトする。Supabase Auth の新規サインアップは無効化する

### **6.2 メール到達性・法令対応**

* **送信ドメイン認証:** Resend で独自ドメインを認証し、**SPF / DKIM / DMARC** の DNS レコードを設定する（これが無いとステップ配信は高確率で迷惑メールに入る）
* **特定電子メール法対応:** 全メールのフッターに以下を必ず含める（`delivery_accounts.legal_footer`）
  * 送信者（事業者）の氏名または名称
  * 住所
  * **解除用リンク**
  * 問い合わせ先メールアドレス
* **List-Unsubscribe ヘッダー:** ワンクリック解除に対応するため、`List-Unsubscribe` および `List-Unsubscribe-Post` ヘッダーを付与する
* **解除の即時性:** メルマガ解除後は、既にキューに積まれているメールも送信しない（送信直前のフィルタで判定する）

### **6.3 パフォーマンス**

* 販売ページの初期ロード（SSR）でのDBアクセスを高速化するため、5.3 のインデックスを設定する
* **送信バッチの1回あたりの処理上限は500件**とする。根拠は以下（詳細は 7.2）。
  * 実行時間：Batch APIで5リクエスト（≒2.5秒）＋DB更新。Edge Function の上限400秒に対して十分余裕がある
  * **CPU時間の上限が2秒**（I/O待ちは除く）のため、置き換え文字の解決を行う件数を無制限にはしない
  * 500件を超える分は次回実行（1分後）に持ち越す。**1分間隔なので理論上 毎時30,000通** まで捌け、Resend Pro の月間上限（50,000通）を大きく上回る
* 送信対象の抽出クエリは `deliveries(status, scheduled_at)` の複合インデックスを使う。このクエリが毎分実行されるため、テーブル肥大時の性能劣化に最も注意する

### **6.4 信頼性**

* **送信の冪等性:** `UNIQUE(scenario_reader_id, step_message_id)` と `status=processing` への事前更新により、Cronの二重実行やリトライで同じメールが2度送られないことを保証する
* **タイムゾーン:** DBは全て `timestamptz`（UTC保存）とし、管理画面の表示と `send_at_hour` の解釈は **Asia/Tokyo** で行う
* **カウントダウンの信頼性:** 残時間はサーバーが返す `deadline_at` を基準に算出し、クライアントの時計をずらしても期限が延びないようにする。最終判定は必ずサーバーサイドで行う

## **9. 未決事項・今後の検討課題**

以下はMVPの実装をブロックしないが、運用開始前後に判断が必要。

1. **デッドラインの具体的な長さ**
   登録起点を何時間にするか（例：72時間）。購入起点は7日で確定。※ `funnels.deadline_hours` で設定可能なため、実装後に調整できる。

2. **ステップ配信の通数と間隔**
   GUIで編集できるため実装をブロックしないが、初期シナリオの設計は別途必要。

3. **Substack との運用上の使い分け**
   本ツールとSubstackで同じ読者に二重配信しないためのルール（例：本ツールはファネル中のみ配信し、平常時の配信はSubstackに任せる）。システム連携はしないため、運用ルールとして決める。

4. **将来クライアントに提供する場合の送信ドメイン**
   クライアントごとに差出人ドメインを分ける場合、Resend でクライアント分のドメインを認証する必要がある。`delivery_accounts.from_email` を持たせてあるため対応は可能。
   * **Resend Pro の検証済みドメイン枠は10個**（7.4）。自分の1ドメインを除くと**クライアントは最大9社**まで。それ以上は Scale プランへの移行が必要
   * DNS設定（SPF/DKIM/DMARC）をクライアントに依頼する運用が発生する

5. **Vercel Hobbyプランの商用利用可否 ★要判断**
   Hobbyプランは**規約上、商用利用が制限される**（7.3）。本ツールはStripe決済で売上が発生するため、**本番運用に入る時点で Pro（月$20）への移行がほぼ必須**。
   * ただしこれは**規約上の判断のみ**で、技術的には Hobby のままで動作する（Cron要件は Supabase 側で解決済み）
   * Pro移行時は月額固定費が $45 → $65 になる
   * Vercel Pro に移行すれば Vercel Cron も分単位で使えるようになるが、その時点で送信基盤を移す必要はない（Supabase側の構成のまま運用する）

6. **UTAGEの読者項目（カスタム項目）をどこまで持つか**
   UTAGEはシナリオごとに任意の読者項目を定義できる。本ツールは `readers.custom_fields`（jsonb）で受け皿だけ用意しているが、**項目定義のUIは持たない**。UTAGEから多くの項目を持つ読者を取り込む場合、この方針で足りるか要確認（10.2）。

7. **スコープ外とした機能の再検討タイミング**
   開封/クリック計測、バウンス処理、ラベルによる配信条件分岐、シナリオ遷移（アクション設定のフル機能）、一斉配信、LINE配信は、運用データが溜まってから必要性を判断する。

## **10. UTAGEとの相互運用（双方向CSV）**

**両方向の移行を想定する。**（本ツール → UTAGE、UTAGE → 本ツール）

### **10.1 エクスポート（本ツール → UTAGE）**

UTAGEの「読者一覧 > 追加 > **CSV一括追加**」にそのまま投入できる形式で出力する。

* **出力単位は「シナリオごと」**。UTAGEでは読者がシナリオに属するため、テナント全体の一括エクスポートではなく、シナリオを選んで出力する
* 出力カラム：`メールアドレス`, `名前`, `登録日時`, `登録経路`, `ラベル`（複数はカンマ区切り）, `購入状況`, `解除状況`, + `custom_fields` の各キー
* **ヘッダー行は日本語**（UTAGEの読者項目名と一致させるため）
* 文字コードは **UTF-8 BOM付き**（Excelでの文字化けを防ぐ）

### **10.2 インポート（UTAGE → 本ツール）★事故防止が最重要**

UTAGEからエクスポートした読者CSVを取り込めるようにする。

**必須要件：既存読者への再送を防ぐオプション**

UTAGEのCSV一括追加には「登録直後／以降のステップ配信・リマインダ配信の対象にするか否か」を選ぶチェックボックスがあり、**これを誤ると移行した全読者に1通目から全ステップが再送される**。本ツールのインポートにも同等のオプションを必ず設ける。

| オプション | 挙動 |
| :---- | :---- |
| **ステップ配信の対象にしない**（デフォルト） | 読者と `scenario_readers` だけを作成し、`deliveries` を一切キューに積まない。**静かに移行したい場合** |
| 途中から配信する | `registered_at` を指定日時にして、**その時点以降のステップのみ**キューに積む |
| 最初から配信する | 全ステップをキューに積む（新規読者と同じ扱い） |

**その他の要件**

* インポートは**必ずドライラン（取り込み件数・重複件数のプレビュー）を挟む**。UTAGEのマニュアルでも「実行ボタンは必ず1度だけクリック」と注意されており、二重実行の事故が起きやすい
* 既存の `readers`（同一 `tenant_id` + `email`）は**更新扱い**とし、重複作成しない
* CSV内のラベル列は、存在しないラベルを自動作成して付与する
* 未知のカラムは `custom_fields` に格納する
* インポート処理は冪等にする（同じファイルを2回流しても結果が変わらない）

### **10.3 UTAGEへ移行する場合の手順（想定）**

1. **1テナント = 1 UTAGE契約** を用意する（UTAGEにテナント分離はない。1.5 参照）
2. UTAGE側で **配信アカウント**（メールのみ）と **シナリオ** を作成する
3. UTAGE側で **ラベル** を作成する（本ツールのラベル名と一致させる）
4. 本ツールから **シナリオごとに読者CSVをエクスポート**（10.1）
5. UTAGEの **CSV一括追加** で取り込む。このとき **「ステップ配信の対象にする」のチェックを外す**（既存読者への再送防止）
6. **ステップ配信の本文を手作業で移植する**（置き換え文字の記法がUTAGEと異なるため、機械変換はしない）
7. 商品・決済は UTAGE の**商品管理**と**決済連携設定**で作り直す（Stripeの Price ID は流用可能）
8. 会員サイトは UTAGE の**コース**として作り直す（本ツールは動画URLを持つだけなので移植は軽い）

> **移植が手作業になる部分:** ステップ配信の本文、ページのデザイン、商品・決済設定。**自動で持ち運べるのは読者データとラベル**。この線引きを前提に、本文はUTAGEでも使える書き方（凝ったHTMLを避ける）を心がける。

### **10.4 移行容易性のための設計ルール**

以降の実装では、以下を守ることで移行コストを低く保つ。

1. **1.5 の対応表にない用語をコード・UIに持ち込まない。** 新しい概念が必要になったら、まずUTAGEに対応語があるか確認し、対応表を更新してから実装する
2. **UTAGEに存在しない機能を安易に足さない。** 足す場合は「UTAGE移行時にこの機能は失われる」と 9章 に明記する
3. **メール本文にツール固有の凝った仕組みを持ち込まない**（条件分岐、動的ブロック等）。置き換え文字による単純な差し込みに留める
4. **ラベルの命名規則をUTAGEでもそのまま使えるものにする**（例：`プレゼントA登録`、`フロント動画購入`）
