## 設計の要点

### claim: FOR UPDATE SKIP LOCKED → 単発の UPDATE ... RETURNING

D1 は単一 writer で書き込みが直列実行されるため、Postgres の `FOR UPDATE SKIP LOCKED` は不要。
`claimDueDeliveries` は1本の `UPDATE ... WHERE id IN (SELECT ... LIMIT n) RETURNING ...` で
「候補選択＋processing 化＋attempt_count インクリメント」を原子的に行う。cron の重複実行が
あっても同じ行を二重に claim できない。並び順（scheduled_at, id）・スタック復旧（10分）・
リトライ上限（3回）・batch 上限（500）は Postgres 版と同値。

### 送信条件フィルタは SQL から TypeScript の純関数へ

Postgres 版は claim RPC 内の join で「解除済み / 停止・完了 / 購入済みスキップ」を判定していたが、
P4 時点で readers / scenario_readers / step_messages / scenarios / purchases は Supabase 側に残るため
join できない。Worker が Supabase から判定材料を引き、`shouldSkipDelivery`（純関数・テスト済み）で
判定して `markDeliveriesSkipped` を呼ぶ。**意味論は Postgres 版と同一**（対象商品未設定なら
テナント内の任意購入でスキップ、購入起点シナリオは判定対象外、を含む）。

### 時刻は UTC ISO 8601 文字列

SQLite に timestamptz が無いため text で持つ。`toQueueTimestamp` の形式（UTC・ミリ秒3桁・Z）なら
文字列比較＝時刻比較になり、`(status, scheduled_at)` インデックスが効く。
**この形式以外で書き込むコードを混ぜないこと**（比較が静かに壊れる）。

### rows read 課金

D1 の rows read は「スキャンした行数」。sent/skipped が溜まった状態で毎分フルスキャンすると
課金が線形に増えるため、claim の候補選択が `deliveries_status_scheduled_at` インデックスを
使うことをテストで固定した（EXPLAIN QUERY PLAN を検証。インデックスを消すとテストが落ちる）。

### 処理件数上限（要件定義書 7.5 #4 の「500件」）

旧値の根拠（Edge Function の実行時間制限）は Workers の CPU 制限（有料プランで15分）により消える。
ただし Resend Batch API の 100通/回、D1 の応答サイズ、1分間隔 cron との重なりを考えると、
**上限を上げるのは実測（毎分の処理時間・rows read）を見てからでよい**。コード上は
`DELIVERY_CLAIM_MAX_BATCH = 500` を上限として維持している。

## DB が2つに割れる期間の整合性（issue の注意点への回答）

`deliveries` だけ D1 に移すと、以下の書き込みがデータベース境界を跨ぐ。

| 経路 | 現状 | P4 後 | 壊れ方と対処 |
|---|---|---|---|
| `register_reader`（読者登録→キュー投入） | 1トランザクション | Supabase 書き込み成功 → D1 投入失敗 がありうる | UNIQUE(scenario_reader_id, step_message_id) があるため**再投入は冪等**。登録処理の最後に D1 投入し、失敗したら登録全体をエラーにせず「キュー未投入」をログ＋リトライキューへ。**scenario_readers にあるのに deliveries が無い行を検出する突き合わせジョブ（日次）を移行期間中は必ず動かす** |
| `process_stripe_purchase`（購入→シナリオ開始） | 同上 | 同上 | 同上（同じ突き合わせで検出可能） |
| CSVインポート RPC（deliveries を一括投入） | 1トランザクション | RPC から deliveries の insert を外し、アプリ側で D1 へ投入 | バッチ途中失敗の「先頭からn行反映済み」に「キュー投入済みか」の軸が増える。**P4 での移行対象から外し、インポートのキュー投入は最後に移すことを推奨** |
| dispatch（claim→送信→結果反映） | Edge Function + RPC | Worker + D1 のみで完結 | 跨がない（表示素材の read は Supabase だが、書き込みは D1 に閉じる） |

**結論: 読み書きが単純なのは dispatch 側だけで、キュー投入側は跨ぐ。** 移行順は
「dispatch を D1 化 → 投入経路を1本ずつ D1 へ → 最後に CSV インポート」とし、その間は
突き合わせジョブを保険にする。

## 移行手順（実施は契約後）

1. `wrangler d1 create uotage-deliveries` → `wrangler.jsonc` に binding 追加（PR #14 の `workers/dispatch-cron` に統合）
2. `wrangler d1 migrations apply uotage-deliveries --remote`（`cloudflare/d1/migrations/`）
3. Worker に dispatch ループを実装（残作業参照）。**この時点では D1 は空でキューが無いだけなので、既存の pg_cron + Edge Function 経路と並走しても二重送信は起きない**
4. 既存データ移送: pg_cron / Edge Function を停止 → `queued` / `processing` の行を CSV でエクスポート（`processing` は `queued` に戻してから）→ `wrangler d1 execute --file` で投入 → 件数を突き合わせ → Workers cron 有効化
5. 投入経路（register_reader / process_stripe_purchase）の D1 化は別 PR
6. Supabase 側 `deliveries` と `claim_deliveries` RPC は**切り戻しに備えて残す**（削除は安定運用後）

ロールバック: Workers cron を止め、D1 の `queued` 行を逆向きに移送して pg_cron を再開。
手順 4 と対称なので、移送スクリプトは双方向で書くこと。
